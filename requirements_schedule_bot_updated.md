# Требования к персональному боту расписания

## 1. Назначение

Разработать персонального Telegram-бота, который автоматически получает расписание учебной группы с сайта МИГиАиК и позволяет быстро получать расписание без ручного открытия сайта, выбора группы и поиска нужной даты.

Система предназначена только для одного пользователя и одной заранее заданной учебной группы.

---

## 2. Исходные данные

### Сайт расписания

Источник расписания:

`https://study.miigai.ru/`

На момент подготовки требований в браузере открыта страница расписания:

`https://study.miigai.ru/?orgId=2&groupId=1999&dateStart=2026-08-31&dateEnd=2026-09-06`

### Организация

МИИГАиК.

В URL присутствуют параметры:

- `orgId=2` — идентификатор организации;
- `groupId=1999` — идентификатор учебной группы;
- `dateStart=2026-08-31`;
- `dateEnd=2026-09-06`.

### Учебная группа

**ИБО-26-2**

Группа уже сохранена/выбрана на странице сайта. В интерфейсе отображается:

> ИБО-26-2

Ключевое требование: **бот не должен каждый раз спрашивать или вводить название группы**. Идентификатор группы и/или URL должны быть сохранены в конфигурации приложения.

---

## 3. Что пользователь хочет получить

Основной пользовательский сценарий:

1. Пользователь не открывает сайт вручную.
2. Система сама получает актуальное расписание.
3. Пользователь открывает Telegram.
4. В личном чате с ботом может запросить расписание.
5. Бот возвращает расписание на нужный день.
6. Дополнительно бот автоматически отправляет расписание на завтра в заданное время.

---

## 4. Пользователь

Система рассчитана на:

- одного пользователя;
- одну учебную группу;
- одну организацию;
- один Telegram-аккаунт.

Многопользовательская регистрация, выбор групп другими пользователями, права администратора и обработка нескольких учебных групп **не требуются**.

Для безопасности желательно разрешить работу бота только одному заранее известному Telegram `chat_id` / `user_id`.

---

# 5. Функциональные требования

## 5.1. Получение расписания

Бот должен уметь получать расписание группы **ИБО-26-2** с сайта МИГАиК.

Приоритетный порядок получения данных:

1. Найти и использовать официальный API сайта, если оно доступно.
2. Если API отсутствует — выполнять HTTP-запросы к страницам/эндпоинтам сайта.
3. Если сайт формирует данные динамически через JavaScript — использовать Playwright или аналогичный браузерный автоматизатор.
4. Не использовать OCR, если расписание доступно как HTML/JSON/таблица.

---

## 5.2. Определение структуры сайта

Перед реализацией необходимо исследовать сайт и установить:

- существует ли API;
- какие HTTP-запросы выполняются при выборе группы;
- как передаётся `groupId=1999`;
- как передаётся диапазон дат;
- где находится расписание в HTML/JSON;
- требуется ли JavaScript;
- требуется ли авторизация;
- существуют ли дополнительные внутренние идентификаторы занятий;
- как обрабатываются переходы между неделями.

Если данные доступны напрямую через API, браузерную автоматизацию не использовать без необходимости.

---

## 5.3. Сохранённые настройки

В конфигурации должны быть сохранены:

```text
organization_id = 2
group_id = 1999
group_name = ИБО-26-2
source_url = https://study.miigai.ru/
```

Telegram:

```text
telegram_bot_token = секрет
allowed_user_id = секрет
```

Расписание и служебные данные должны храниться отдельно от секретов.

Токен Telegram-бота не должен находиться в открытом исходном коде.

# 6. Команды Telegram-бота

Минимальный набор:

### `/start`

Проверяет пользователя и выводит краткую инструкцию.

Пример:

> Бот расписания МИИГАиК  
> Группа: ИБО-26-2  
>
> /today — расписание на сегодня  
> /tomorrow — расписание на завтра  
> /week — расписание на текущую неделю

### `/today`

Показывает расписание на текущий день.

### `/tomorrow`

Показывает расписание на следующий календарный день.

### `/week`

Показывает расписание на текущую учебную неделю.

### `/next`

Показывает ближайшее следующее занятие.

Дополнительные команды можно добавить после MVP.

---

# 7. Формат сообщения

Расписание должно быть компактным и удобным для чтения в Telegram.

Пример:

```text
📅 Завтра — 02.09.2026
👥 ИБО-26-2

2️⃣ 10:40–12:10
Основы права
Практическое занятие
👨‍🏫 Новичков Андрей Вячеславович
📍 Аудитория 1308

3️⃣ 12:30–14:00
Информатика
Лабораторные занятия
👩‍🏫 Попова Екатерина Сергеевна
📍 Аудитория 1409
```

Для каждого занятия желательно показывать:

- номер пары;
- время начала;
- время окончания;
- название дисциплины;
- тип занятия;
- преподавателя;
- аудиторию.

---

# 8. Работа с днями без занятий

Если на выбранную дату занятий нет:

```text
📅 01.09.2026

Занятий нет.
```

При запросе `/tomorrow` желательно явно указать, что занятий нет, а не возвращать пустое сообщение.

---

# 9. Автоматическое ежедневное уведомление

Система должна иметь возможность автоматически отправлять расписание на завтра.

Пример:

```text
Каждый день в 19:00
        ↓
получить расписание на завтра
        ↓
сформировать сообщение
        ↓
отправить пользователю в Telegram
```

Пример:

> 📚 Расписание на завтра  
> ИБО-26-2  
>
> 3 пары:
>
> 09:00–10:30 — Основы исследований информационной безопасности — ауд. 2408  
> 10:40–12:10 — Основы исследований информационной безопасности — ауд. 2210  
> 12:30–14:00 — Безопасность жизнедеятельности — ауд. 1406

Время отправки должно быть настраиваемым.

---

# 10. Кэширование расписания

Для уменьшения количества обращений к сайту желательно сохранять уже полученное расписание.

Например:

```text
дата
номер пары
время
дисциплина
тип занятия
преподаватель
аудитория
```

При команде `/tomorrow` бот сначала может использовать актуальные сохранённые данные.

Если данные устарели — выполнять обновление.

---

# 11. Проверка изменений расписания

Желательная функция второго этапа.

Система должна периодически получать расписание и сравнивать его с предыдущей версией.

Нужно обнаруживать:

- добавление занятия;
- удаление занятия;
- перенос занятия;
- изменение времени;
- изменение аудитории;
- изменение преподавателя;
- изменение типа занятия;
- изменение названия дисциплины.

Пример уведомления:

```text
⚠️ Изменение расписания

03.09.2026, 2 пара

Основы исследований информационной безопасности

Было:
📍 Аудитория 2210

Стало:
📍 Аудитория 2315
```

---

# 12. Работа с недельным расписанием

Скриншот показывает, что сайт работает с недельным диапазоном:

```text
31.08.2026 — 06.09.2026
```

Следовательно, парсер должен уметь:

- получать текущую неделю;
- получать следующую неделю;
- получать предыдущую неделю;
- преобразовывать недельный диапазон в конкретные даты;
- находить нужный день внутри недели.

Не следует полагаться только на текущий HTML, если переход на другую неделю выполняется отдельным запросом.

---

# 13. Навигация по неделям

На сайте присутствуют элементы перехода к предыдущей и следующей неделе.

Необходимо определить, как они реализованы:

- изменение URL;
- AJAX/fetch;
- изменение query-параметров;
- POST-запрос;
- состояние JavaScript-приложения.

В итоговой реализации предпочтительно использовать прямой запрос к источнику данных, а не программно нажимать кнопки, если это возможно.

---

# 14. Работа в выходные и праздничные дни

Бот должен корректно работать с датами, на которые занятий нет.

Проверка должна учитывать реальное расписание, а не предполагать наличие пары только потому, что это будний день.

---

# 15. Временная зона

Все даты и время расписания должны интерпретироваться в часовом поясе учебного заведения/пользователя.

Часовой пояс необходимо сделать параметром конфигурации.

Предполагаемое значение:

```text
Europe/Moscow
```

Но перед реализацией оно должно быть подтверждено по фактическому времени работы сайта.

---

# 16. Архитектура

Предпочтительная архитектура для первого варианта:

```text
                 ┌──────────────────────┐
                 │ Сайт study.miigai.ru │
                 └──────────┬───────────┘
                            │
                       API / HTTP
                            │
                            ▼
                    ┌───────────────┐
                    │ Python Parser │
                    └───────┬───────┘
                            │
                     расписание
                            │
                  ┌─────────▼─────────┐
                  │ Кэш / SQLite      │
                  └─────────┬─────────┘
                            │
                  ┌─────────▼─────────┐
                  │ Telegram Bot      │
                  └─────────┬─────────┘
                            │
                            ▼
                       Пользователь
```

Отдельный планировщик:

```text
Scheduler
   ↓
Python
   ↓
обновить расписание
   ↓
сохранить
   ↓
при необходимости отправить уведомление
```

# 17. Инфраструктура

## Вариант MVP

Для первой версии желательно избежать обязательной аренды VPS.

Рассмотреть:

- GitHub Actions для периодического обновления расписания;
- serverless/backend для Telegram webhook;
- либо запуск на собственном компьютере.

## Ограничение GitHub Actions

GitHub Actions подходит для периодических задач:

```text
получить расписание
→ сохранить данные
→ отправить уведомление
```

Но не следует использовать GitHub Actions как постоянно работающий Telegram polling-процесс.

Для мгновенной обработки команд Telegram лучше использовать webhook/backend или другой постоянно доступный механизм.

---

# 18. Секреты

Следующие значения должны храниться в Secret/Environment Variables:

```text
TELEGRAM_BOT_TOKEN
ALLOWED_TELEGRAM_USER_ID
```

Не хранить их:

- в GitHub репозитории;
- в README;
- в публичном `.env`;
- непосредственно в Python-коде.

---

# 19. Логирование

Необходимо логировать:

- запуск парсера;
- успешное получение расписания;
- количество найденных занятий;
- ошибки HTTP;
- ошибки разбора;
- ошибки Telegram API;
- изменения расписания.

В логах не должны присутствовать Telegram Bot Token и другие секреты.

---

# 20. Обработка ошибок

Если сайт временно недоступен:

```text
Сайт недоступен → повторная попытка → запись ошибки → уведомление только при необходимости
```

Если расписание не удалось распарсить:

> ⚠️ Не удалось получить актуальное расписание. Попробую обновить данные позже.

Если Telegram временно недоступен — ошибка должна логироваться, а задача должна иметь возможность повторного выполнения.

---

# 21. Критически важные проверки

Перед окончательной реализацией необходимо подтвердить:

1. `groupId=1999` действительно соответствует группе **ИБО-26-2**.
2. `orgId=2` соответствует МИИГАиК.
3. Можно ли получать расписание напрямую без эмуляции браузера.
4. Как сайт получает расписание при изменении даты.
5. Есть ли API.
6. Какой формат данных возвращает API.
7. Как определяется начало/конец недели.
8. Как представлены занятия внутри данных.
9. Нужно ли учитывать несколько вариантов занятия для одной пары.
10. Есть ли авторизация или дополнительные cookies/tokens.

---

# 22. MVP

Первая рабочая версия должна уметь только следующее:

- использовать заранее заданную группу **ИБО-26-2**;
- получить расписание с сайта;
- определить расписание на конкретную дату;
- работать через Telegram;
- принимать `/today`;
- принимать `/tomorrow`;
- принимать `/week`;
- отправлять результат только разрешённому пользователю;
- автоматически отправлять расписание на завтра по расписанию;
- корректно сообщать об отсутствии занятий.

---

# 23. Второй этап

После MVP добавить:

- `/next`;
- кэширование;
- автоматическое обновление;
- обнаружение изменений;
- уведомления об изменениях;
- более удобное форматирование;
- хранение истории расписания.

---

# 24. Что не требуется

На текущем этапе НЕ нужны:

- регистрация пользователей;
- выбор группы;
- поддержка нескольких групп;
- Telegram-группы;
- роли пользователей;
- админ-панель;
- мобильное приложение;
- веб-интерфейс;
- полноценная CRM;
- публичный доступ к боту.

---

# 25. Итоговая цель

Пользователь должен полностью избавиться от ручного сценария:

```text
Открыть сайт
→ найти расписание
→ выбрать группу
→ выбрать неделю
→ найти завтра
→ прочитать пары
```

Вместо этого:

```text
Telegram
   ↓
/tomorrow
   ↓
готовое расписание
```

Или вообще без запроса:

```text
19:00
   ↓
бот автоматически
   ↓
📚 Расписание на завтра
```
